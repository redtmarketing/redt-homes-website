# Tying Listing Page Form Submissions to Properties in HubSpot

This describes the one-time HubSpot setup needed so that when someone fills out
the inquiry form on a specific listing page (e.g. `/listings/2442-s-saint-paul-street-denver.html`),
that submission shows up in HubSpot tied to that specific property — not just as
a generic contact.

**Where this stands today:** listings come from a manually-maintained
spreadsheet (`listings/property_listings.xlsx` → `data/listings.json`), not a
live MLS/IDX feed, so "connecting MLS to HubSpot" in practice means keeping
one consistent identifier for each property across three places: the
listing's webpage, its hidden form fields, and its record in HubSpot. There's
no automated data feed to configure — this is a manual-but-consistent
process, matching how listings are managed today. If you later add a real
IDX/MLS vendor feed, see "Future: adding a live MLS feed" at the bottom.

## How the website side already works

Every page in `/listings/` is generated by `build-listings.js` from
`data/listings.json`, and each one has a form with six hidden fields already
baked in:

```html
<input type="hidden" name="listing_id" value="2442-s-saint-paul-street-denver">
<input type="hidden" name="listing_mls_id" value="8237503">
<input type="hidden" name="listing_address" value="2442 S Saint Paul Street, Observatory Park, Denver, CO">
<input type="hidden" name="listing_price" value="$5,500,000">
<input type="hidden" name="listing_status" value="Move-in Ready">
<input type="hidden" name="listing_url" value="https://www.redthomes.com/listings/2442-s-saint-paul-street-denver.html">
```

`listing_id` is the important one for the website side — it's a stable slug
(matches the filename) that never changes even if price/status details are
edited later. `listing_mls_id` is the real numeric MLS ID from the source
data, which may be more useful as the join key on the HubSpot/CRM side if
your team already thinks in MLS numbers. Pick one as the canonical key and
use it consistently everywhere in HubSpot — don't mix the two.

All 19 current listings now have a real `hubspotFormId` in `data/listings.json`,
so every listing page renders a **live** HubSpot embed using the JS API (so
the hidden fields get prefilled on load):

```html
<div id="hubspotForm-2442-s-saint-paul-street-denver"></div>
<script src="https://js.hsforms.net/forms/embed/v2.js"></script>
<script>
  hbspt.forms.create({
    portalId: "43826586",
    formId: "9f75e3f1-c3e8-4026-8f72-c75b9838bbe3",
    target: "#hubspotForm-2442-s-saint-paul-street-denver",
    onFormReady: function ($form) {
      var formEl = ($form && $form.get) ? $form.get(0) : ($form && $form[0]) || $form;
      function setHiddenValue(name, value) {
        var el = formEl.querySelector('input[name="' + name + '"]');
        if (el) el.value = value;
      }
      setHiddenValue("listing_id", "2442-s-saint-paul-street-denver");
      setHiddenValue("listing_mls_id", "8237503");
      setHiddenValue("listing_address", "2442 S Saint Paul Street, Observatory Park, Denver, CO");
      setHiddenValue("listing_price", "$5,500,000");
      setHiddenValue("listing_status", "Move-in Ready");
      setHiddenValue("listing_url", "https://www.redthomes.com/listings/2442-s-saint-paul-street-denver.html");
    }
  });
</script>
```

Use the **JS API** (`hbspt.forms.create`), not the plain `<script src="...">`
embed snippet HubSpot offers by default — the plain embed can't have its
fields prefilled by your page, which is the whole point here. The
`onFormReady` callback uses plain DOM `querySelector` rather than jQuery's
`.find()`, since this site doesn't load jQuery and HubSpot's v2 embed passes
a plain DOM element (not a jQuery object) when jQuery isn't present on the
page — using `.find()` here throws `$form.find is not a function` in the
browser console.

**Portal ID `43826586` is baked into every listing page.** If you add a new
listing to `data/listings.json` before you have its HubSpot form ID, leave
`hubspotFormId` as `""` — `build-listings.js` will fall back to a plain,
non-submitting placeholder form on that page (and print a reminder when you
run it) until you fill the ID in and re-run the build.

**The hidden fields only populate if the HubSpot form itself has matching
hidden fields** named `listing_id`, `listing_mls_id`, `listing_address`,
`listing_price`, `listing_status`, `listing_url` (see Option A step 1 below).
Until that one-time setup is done per form, the embed still renders and
works — the hidden-field prefill silently no-ops instead of erroring.

## HubSpot setup — Option A: simple (recommended to start)

No custom objects, no workflows. Every contact record just carries which
property they asked about, which you can filter, report, and route on.

1. **Create the form fields.** In your HubSpot form (Marketing → Forms), add
   hidden fields with these exact internal names: `listing_id`,
   `listing_mls_id`, `listing_address`, `listing_price`, `listing_status`,
   `listing_url`. Set each one's field type to "Single-line text" and mark it
   hidden (not shown to the visitor).
2. **Create matching Contact properties.** In Settings → Properties → Contact
   properties, create custom properties with those same internal names
   (HubSpot will offer to reuse the form field's internal name — say yes).
3. **Map the form fields to those properties** when building the form (HubSpot
   does this automatically if the internal names match).
4. Done. Every submission from a listing page now populates those fields on
   the resulting Contact record. You can:
   - Filter/segment contacts by `listing_id`, `listing_mls_id`, or `listing_address`
   - Build a list or report per property
   - Trigger a workflow off "Form submission" filtered by `listing_id = ...`
     to notify the right salesperson for that listing

This gets you "tied to that specific property" without needing a HubSpot plan
that supports custom objects.

## HubSpot setup — Option B: advanced (a "Listings" custom object)

Do this if you want a real relational model — one Listings record per
property, with every inquiry associated to it (useful once you have many
concurrent listings and want a single record showing all activity on one
property). Requires a HubSpot plan with custom objects (Sales/Marketing/
Service Hub Enterprise, or Operations Hub Starter+).

1. **Create the custom object.** Settings → Data Management → Objects →
   Create custom object, name it `Listing`, with properties: `Listing ID`
   (your `listing_id` slug — mark it required and unique), `MLS ID`, `Address`,
   `Price`, `Status`, `URL`.
2. **Create one Listing record per property** — the 19 rows in
   `data/listings.json` map 1:1 to Listing records. The `Listing ID` value
   must exactly match that page's `listing_id` hidden field.
3. **Set up the form** exactly as in Option A (hidden fields → matching
   Contact properties) — you still need `listing_id` to land somewhere
   readable on the Contact/submission so a workflow can act on it.
4. **Build a workflow** (Automation → Workflows) enrolled on "Form submitted"
   for each listing form (or filtered by which `listing_id` was submitted):
   - Action: "Find or create association" / a custom-coded workflow action
     that searches the `Listing` object for a record where `Listing ID` equals
     the contact's `listing_id` property, then associates the Contact (and/or
     the Deal, if you create one per inquiry) with that Listing record.
   - HubSpot's native workflow actions for finding-and-associating custom
     object records vary by plan; if the visual workflow builder doesn't
     expose this directly, this step may need a HubSpot Operations Hub
     "Custom coded action" (a small JavaScript/Python snippet using the
     HubSpot API) — your HubSpot admin or a HubSpot partner can set this up
     from the identifiers already described above.

## Naming convention — keep this consistent

Whichever option you use, pick either `listing_id` (slug) or `listing_mls_id`
(real MLS number) as the single source-of-truth key and use it everywhere:
the hidden form field, the Contact property, and (if you go with Option B)
the Listing custom object's unique identifier. Don't mix keys or rename them
per-listing — the same internal property/field name must be used across
every listing page and every HubSpot form.

## Future: adding a live MLS feed

If you later connect a real IDX/MLS data feed (e.g. via an IDX vendor like
iHomefinder, or a direct RESO Web API feed from your MLS), that feed becomes
the source of truth for listing data instead of the spreadsheet/JSON. At that
point you'd typically:

- Use the vendor's existing HubSpot integration (several IDX providers have
  one), or
- Sync the feed into the HubSpot `Listing` custom object via middleware
  (Zapier, Make, or a custom script hitting HubSpot's CRM API) keyed on the
  same `Listing ID`/MLS number, or
- Have your MLS/IDX vendor push listing changes to HubSpot directly if their
  integration supports it.

None of this requires changing the naming convention above — the hidden
`listing_id` / `listing_mls_id` fields on each page are designed to be the
stable join key whether listings are entered by hand (as now, via the
spreadsheet) or synced from a live feed later.
